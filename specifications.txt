VIVID CHAT TECHNICAL SPECIFICATIONS
===================================

1. CORE ARCHITECTURE & MULTI-BOT RUNTIME
---------------------------------------
* Dynamic Multi-Bot Discovery: Bots are discovered dynamically from the `TELEGRAM_TOKENS` mapping in `config.yaml` (`{bot_name: token}`).
* Multi-Tenancy & Concurrency: All configured bots run concurrently in a single async event loop via `run_all_bots(bot_instances)`. Each bot maintains its own independent `BotInstance` state, context, active role/story, and Telegram updater.
* Bot CLI Filtering: Optionally pass a bot name as an argument (`python vivid.py chat1`) to run only a single targeted bot.
* Mutual Exclusion & Usage Tracking:
    - `BotUsageTracker` (backed by `settings/bot_assignments.json`) prevents any two bots from using the same chat/role or story at the same time.
    - If a bot attempts to switch to an in-use role or story, the action is rejected with a message showing which bot currently holds it.
    - On startup, if a bot's preferred role or story is already in use by another bot, it automatically falls back to an unassigned role or story.
* Configuration: Loads from `config.yaml`. Supports path overrides via `config.paths.yaml`.
* Provider Support:
    - Ollama (Local/Online): AsyncClient handling multiple host URLs and API keys.
    - OpenAI-Compatible: Standard `/v1` endpoints with custom headers and fallback `/models`.
    - Gemini: `genai.Client` using Google API keys.
* Persistence:
    - Automatically loads each bot's `[bot_name]_last_session.json` from `chats_stories/chats/session/` on startup.
    - Atomic Save Pattern: Writes to `.tmp` file then atomically replaces target to prevent corruption.
    - Encoding: UTF-8 with `ensure_ascii=False` to preserve emojis and non-Latin text.

2. COMMAND SYSTEM
-----------------
* Trigger: `PrefixHandler` captures '.' (dot) commands.
* Per-Bot Command Resolution: `get_bot(context, update)` resolves the active `BotInstance` via `context.application.bot_data["bot_instance"]` or Telegram bot ID / token mapping.
* Command Lifecycle:
    1. Input: User sends `.command`.
    2. Identification: `reply_and_log` checks if the user message ID is already in history.
    3. History Entry (User): The command text is added to the bot's `chat_history` with `is_command: True` and its Telegram `msg_ids`.
    4. Execution: The command logic runs (e.g., toggling a setting, switching role/story, or querying models).
    5. Output: Bot responds. `reply_and_log` captures response `msg_ids`, sets `is_command: True`, and appends to history.
    6. Persistence: Active context and `.status` are saved immediately.
* Metadata & Filtering:
    - All commands and their outputs are tagged `is_command: True`.
    - In both Chat and Story modes, payload construction filters these out so the LLM never sees command meta-chatter.
* UI Syncing:
    - Every entry in history tracks its corresponding Telegram message IDs.
    - `context.bot.delete_message` is used to keep the Telegram screen in sync with the bot's memory during "clean" or "delete" operations.

3. CONTEXT & STATUS PERSISTENCE
--------------------------------
* Context Storage Locations:
    - Roles / 1-on-1 Chats: `chats_stories/chats/chat_context/<role_name>.txt`
    - Stories: `chats_stories/stories/<story_name>/story_context/context.txt`
* Context File Format:
    Structured block format with clear user and assistant role headers separated by dashes:
    ```
    user -----------
    <user message>

    assistant -----------
    <assistant response>
    ```
* Context Switching & Reloading:
    - When switching roles (`.role [n]` or `switch_role`):
      1. Current context is formatted and saved to `chat_context/<current_role>.txt`.
      2. Current configuration is saved to `config/<current_role>.status` and `config/.status`.
      3. Previous context and status for target role are reloaded from disk into the bot.
    - When switching stories (`.story select <name>` or `switch_story`):
      1. Current story context is saved to `<story_name>/story_context/context.txt`.
      2. Current configuration is saved to `<story_name>/.status`.
      3. Target story's context and status are reloaded from disk into the bot.
* Status Configuration Storage:
    - Model, provider, role, mode, active characters, active scenes, context limits, and generation options (temperature, top_p, repeat_penalty, etc.) are saved in JSON `.status` files:
      - Roles: `chats_stories/chats/config/<role_name>.status` and `chats_stories/chats/config/.status`
      - Stories: `chats_stories/stories/<story_name>/.status` (and `<story_name>/config/.status`)

4. MEMORY & CONTEXT MANAGEMENT
------------------------------
* Storage: Each `BotInstance` maintains an isolated `chat_history` list of dicts.
* Metadata Schema:
    - role: (system/user/assistant)
    - content: (text string)
    - msg_ids: (list of Telegram IDs for UI deletion)
    - is_command: (bool - used to filter meta-chatter from LLM context)
    - incoming: (bool - tracks user inputs)
* Sliding Window: Logic slices history based on `context_limit`, preserving the system prompt at index 0 and taking the last N messages.
* Sanitization: Before sending to LLM, history is mapped to API payloads (stripping `msg_ids` and `is_command`).

5. DYNAMIC SYSTEM PROMPT CONSTRUCTION
-------------------------------------
Every LLM prompt is prefixed with a composite System Instruction:
1. Role Profile: Content from `chats_stories/chats/roles/[name].txt`.
2. Active Characters: Appends `chats_stories/stories/[story]/characters/[name].txt` for enabled characters.
3. Active Scenes: Appends `chats_stories/stories/[story]/storyelements/[name].txt` for enabled scene settings.
4. Story Backstory: Appends backstory header if present in story context.

6. EXECUTION MODES
------------------
* CHAT MODE:
    - Logic: [System Prompt] + [History Subset (filtered for is_command=False)].
    - Behavior: AI sees a standard conversational thread.
* STORY MODE:
    - Logic: [System Prompt] + [Past Assistant Messages (filtered for is_command=False)] + [Current User Message].
    - Behavior: AI sees only its own past narrative output plus the user's latest steering prompt.

7. I/O LOGIC & TRACING
----------------------
* Message Splitting: Responses > 4000 characters are split into multiple Telegram messages; all resulting IDs are stored in history.
* TRACE MODE:
    - writes `[bot_name]_last_payload.json` (sent to LLM).
    - writes `[bot_name]_last_response.json` (received from LLM).
    - helps debug malformed JSON or prompt-injection issues.

8. SPECIAL WORKFLOWS
--------------------
* .ask (Out of Band):
    - Replaces current system persona with a neutral "Helpful Assistant" instruction.
    - Queries history without appending the question/answer to the session history.
* .resend:
    - Finds last 'user' entry.
    - Removes user prompt and subsequent assistant response from history.
    - Physically deletes the assistant response from the Telegram UI.
    - Re-injects the prompt into handle_message.
* .clear vs .clean:
    - .clear (Memory Wipe): Clears conversation history (keeps active role system prompt).
    - .clean (UI + Memory Wipe): Identical to `.clear`, but also deletes removed messages from Telegram chat.

9. RECAP & SUMMARIZATION
------------------------
* Uses `recap.json` or `roles_summary_prompts.json` as instruction templates.
* Feeds target content (history or role file) to the LLM.
* Outputs are flagged as `is_command=True` so they are excluded from LLM context and cleaned during `.clean`.

10. ERROR HANDLING
------------------
* Network: 60s timeouts for Telegram API.
* Provider: Try/Except blocks for LLM calls with Telegram-side error reporting.
* Path Safety: `exist_ok=True` on directory creation and atomic replacement on writes.
